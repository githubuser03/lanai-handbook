# O1 備份與還原

::: info 本章屬性
- 等級: ● 必要
- 狀態: 可閱讀 (指令未實機驗證)
- 資料基準日: 2026-10-27
- 待查證: Docker 官方 Volumes 頁面的備份與還原段落已核對, 其範例以 `--volumes-from` 搭配 `tar`, 本章範本改為直接掛載具名資料卷, 屬整理者改寫, 指令未實機驗證; 備份與還原演練的具體頻率, 保留份數與檢查表為整理者建議, 無來源 (CISA 只要求「定期」測試, 未給頻率); 備份金鑰的保管方式, CISA 指南未具體說明, 本章做法屬整理者建議; 文中的類比為整理者所寫, 不代表技術上完全等同
:::

**結論**: 要備份的是「資料與設定」, 不是模型檔. 對話資料庫, 向量庫, 設定檔與測試集要定期備份, 並至少一份存放在另一台裝置; 備份沒有還原過, 就不算備份 (信心: 高, 屬通用做法). 頻率建議每週一次 (推論, 信心: 低; 依資料變動量調整).

## O1.1 備份範圍

取捨的原則是: 重新下載就能取回的東西不必備份, 只存在自己這裡的資料一定要備份. 表中的資料卷 (volume) 是容器用來長期保存資料的儲存空間; 向量庫存放文件段落轉成的數字, 供檢索時依意思找出相關段落.

| 對象 | 是否備份 | 說明 |
|---|---|---|
| 介面的資料卷 (對話, 使用者, 設定) | 是 | 以 Open WebUI 為例, 資料存放在掛載到 `/app/backend/data` 的資料卷 (來源: Open WebUI Quick Start) |
| 向量庫資料 | 是 | 重建需要重新嵌入全部文件, 耗時又耗算力. Open WebUI 的資料目錄內含 `vector_db/` (ChromaDB), 隨資料卷一併備份 (來源: Open WebUI 文件 Backups) |
| 原始文件 | 是 | 向量庫只是衍生資料, 原始文件才是來源 |
| 設定檔 (compose 檔, 閘道設定) | 是 | 納入版本控制 |
| `.env` 與金鑰 | 是, 但分開存放 | 與一般備份分開, 限制存取, 不放進同一個備份包 |
| 測試集 ([M6](/build/m6-observability)) | 是 | 回歸測試的依據 |
| 版本紀錄 ([O2](/ops/versioning)) | 是 | 還原時要知道當時的版本 |
| Modelfile 與自訂腳本 | 是 | 體積小, 重建困難 |
| 模型檔 | 否 | 可重新下載; 但要記錄來源與 revision ([M1.5 節](/build/m1-inference)) |

## O1.2 備份做法

原則 (信心: 高, 屬通用做法): 備份前先停止會寫入資料的服務, 以免資料庫檔案處於不一致狀態; 備份檔存放到另一台裝置或另一個磁碟, 並保留多個日期的版本. Open WebUI 文件也建議在冷檔案系統上備份資料庫 (停止服務後備份), 且不要依賴管理介面的資料庫下載功能, 因為它可能漏掉尚在 `webui.db-wal` 的新寫入 (來源: Open WebUI 文件 Backups).

下列範本的三行指令依序是: 停止服務, 用一個暫時的小容器把資料卷打包成壓縮檔, 再重新啟動服務.

**Docker 資料卷的備份範本** (整理者依 Docker 文件 Volumes 頁面的 `tar` 備份做法改寫, 未實機驗證, 執行前請對照該頁; 映像請固定版本標籤):

```bash
docker stop open-webui
docker run --rm -v open-webui:/data -v "$PWD":/backup alpine:<固定版本> \
  tar czf /backup/open-webui-$(date +%F).tar.gz -C /data .
docker start open-webui
```

**備份後立即檢查**:

- [ ] 備份檔大小合理 (不是 0 或異常偏小)
- [ ] 可列出內容: `tar tzf <備份檔> | head`
- [ ] 已複製到另一台裝置或另一個磁碟
- [ ] 記錄備份日期與來源版本

Open WebUI 官方建議每次更新前先備份資料卷 (來源: Open WebUI Quick Start 與 Updating 文件), 因此升級流程應把備份放在第一步 ([O2](/ops/versioning)).

## O1.3 還原演練

沒有演練過的備份, 無法確定能用. 還原演練可以想成消防演練: 平常走過一遍, 真正需要時才知道每一步做得到. 演練時不要動正式環境:

1. 用不同的容器名稱, 資料卷名稱與連接埠 (例如 `127.0.0.1:3001`) 啟動一份新的介面.
2. 把備份檔解開到新的資料卷.
3. 登入並確認: 帳號存在, 舊對話可開啟, 檢索資料可查詢.
4. 記錄耗時與遇到的問題, 更新還原步驟.
5. 刪除演練用的容器與資料卷.

建議每季演練一次, 且在大版本升級前加做一次 (頻率為建議值, 屬推論, 信心: 低).

還原到正式環境時, 先保留現有資料卷, 不直接覆蓋, 確認新環境正常後再清理舊資料.

## O1.4 定期檢查表

| 頻率 | 工作 |
|---|---|
| 每週 | 執行備份並檢查; 檢查安全公告 ([O3](/ops/advisories)) |
| 每月 | 比對 CISA KEV 清單; 評估是否有版本需升級; 檢視備份保留份數與磁碟空間 |
| 每季 | 還原演練; 檢視帳號清單; 檢視金鑰存放位置 |
| 升級前 | 先做一次備份, 並確認該備份可還原 |

## O1.5 備份本身的安全

備份檔含有對話內容與使用者資料, 與正式環境同樣敏感 (信心: 高). 存放備份的裝置要有存取控制; 若備份離開機房或放到雲端, 先加密, 並決定金鑰由誰保管.

美國 CISA 的勒索軟體指南建議三件事: 為關鍵資料保留離線且加密的備份; 備份要離線保存, 因為許多勒索軟體會先找出能存取的備份並刪除或加密; 定期在災難復原情境中測試備份的可用性與完整性 (來源: CISA #StopRansomware Guide). 對手冊讀者, 「離線」可以是平常不接在網路上的外接硬碟. 指南沒有規定加密金鑰怎麼保管, 建議金鑰不要和備份檔放在同一個裝置, 並另外記錄在密碼管理工具或紙本保管處 (整理者建議, 信心: 中).
