**結論**: 地端 AI 的事件多半從「更新時拉到被入侵的版本」或「服務對外暴露」開始. 因此維運的重點是三件事: 知道公告, 能鎖定版本, 能快速輪替金鑰. 若不能每週檢查安全公告, 寧可少裝元件.

## 20.1 公告訂閱

| 管道 | 做法 |
|---|---|
| GitHub Security Advisories | 在每個使用中元件的 GitHub 儲存庫訂閱安全通知 (操作介面可能調整, 請以 GitHub 官方文件為準) |
| 元件發行頁 | 每週檢查一次安全公告; 升級前先讀發行說明 |
| CISA Known Exploited Vulnerabilities (KEV) | 每月比對一次使用中元件是否列入 (頻率為建議值, 屬推論) |
| 本手冊[元件版本與安全公告頁](/ref/versions) | 查看最後驗證日與已知問題 |

## 20.2 案例: LiteLLM 2026 年兩次供應鏈事件

兩次事件的詳細時間線見[第 10.3 節](/deploy/10-gateway). 從維運角度可歸納三個教訓:

1. **浮動標籤不可信**: 2026-10-21 事件中, latest 與 main-stable 標籤都曾指向惡意映像 (LiteLLM 官方事故報告).
2. **事件起點常在上游的小疏失**: 2026-03 事件起於 CI/CD 中未鎖定版本的掃描工具 (Snyk); 2026-10 事件起於 5 月一個 master key 被提交到公開儲存庫 (LiteLLM 官方攻擊鏈分析).
3. **風險集中於保存金鑰的服務**: 閘道集中保存上游金鑰, 一旦入侵, 所有金鑰都須視為外洩.

## 20.3 金鑰輪替與小團隊帳號管理

### 事件處理順序

LiteLLM 兩次事件的官方建議都是「隔離, 重建, 輪替」:

1. **隔離**: 中斷受影響主機的對外網路, 停止相關容器.
2. **重建**: 以已知安全的版本 (依官方公告指定) 重新建立容器與環境, 不在原主機上修補.
3. **輪替**: 更換該主機上存放過的所有金鑰, 包含上游 API 金鑰與資料庫密碼.

### 事先準備

- 列出所有存放金鑰的位置 (`.env`, 閘道設定, 介面設定).
- 上游金鑰只給最低權限並設用量上限, 使外洩損失有上限.
- 演練一次輪替, 確認能在一小時內完成 (信心: 低, 此時間為建議目標, 非來源資料).

### 小團隊帳號

- 每位使用者使用個別帳號, 並關閉公開註冊.
- 人員異動時, 當天停用帳號並檢視其持有的虛擬金鑰.
- 帳號清單每季檢視一次.
