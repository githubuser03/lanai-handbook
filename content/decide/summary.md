# 一頁決策摘要

::: info 本頁屬性
- 等級: 決策參考
- 狀態: 可閱讀 (部分資料待核對)
- 資料基準日: 2026-10-26
- 待查證: 本頁只有兩項外部事實 (開放權重模型的能力差距, 中介層事件) 附來源; 三項前提與建議步驟為整理者判斷框架, 無外部統計; 文中的類比為整理者所寫, 不代表技術上完全等同

**結論**: 自架 AI 在「資料不適合送到外部雲端, 使用量穩定, 且有人固定維運」三項同時成立時才有明顯優勢; 三項沒有同時成立時, 雲端 API 或混合做法通常較省事 (信心: 中, 屬推論).

## 三項判斷前提

自架 AI 是把模型裝在自己的電腦或機房裡執行; 雲端 API 則是透過網路, 把問題送到廠商的模型服務, 依用量付費. 兩者的取捨可以想成自己買車和叫計程車: 天天長途使用, 買車攤下來較划算, 但保養要自己負責; 偶爾才用, 叫車比較省事. 下表從資料, 使用量和維運三個角度, 列出各自較合理的情況.

| 前提 | 自架較合理的情況 | 雲端較合理的情況 |
|---|---|---|
| 資料 | 內部規範或合約要求資料留在自己的環境內 | 資料可交給具備相應保證的雲端服務 |
| 使用量 | 長期穩定且用量高, 能攤提硬體 | 用量小或波動大, 按量計費較划算 |
| 維運 | 有人每週檢查安全公告, 備份與升級 | 沒有固定維運人員 |

模型能力是第四項前提: 開放權重模型 (權重檔可以下載到自己機器上執行的模型) 的能力與雲端旗艦模型之間有差距, 差距是否影響自己的任務, 請用自己的題目實測 (見 [M6](/build/m6-observability)).

## 自架要付出什麼

自架省下按量付給雲端的費用, 換來的是硬體, 人力與風險三種要自己承擔的成本.

- **硬體**: 顯示記憶體 (顯示卡專用的記憶體) 或統一記憶體 (CPU 與 GPU 共用的記憶體) 的容量, 常比運算速度更常決定能跑哪些模型 (見 [K2](/know/k2-quantization)).
- **人力**: 備份, 版本鎖定 (固定使用已驗證的版本), 安全公告, 金鑰輪替 (定期或出事時更換服務之間的存取密碼) 是持續工作, 不是安裝一次就結束的工作 (見 [O1 至 O3](/ops/backup)).
- **風險**: 2026 年已知的事件多出在推論引擎之上的中介層, 也就是介於使用者與模型之間的服務, 例如統一管理金鑰的閘道, 以及用拖拉方塊組流程的低程式碼平台, 而非模型本身 (見[「架構地圖」](/start/map), 細節見 M5, K6, M7).

## 建議的下一步

1. 用[決策樹](/decide/should-self-host)得到初步方向.
2. 用[成本試算表](/decide/tco)填入自己的數字.
3. 用[風險自評](/decide/risk-checklist)確認維運前提.
4. 方向仍是自架時, 用 [30 天 PoC](/decide/poc-30days) 以最小代價驗證, 再決定是否投資硬體.

本手冊不含法規解讀. 涉及資料保護, 契約或產業規範的判斷, 請洽法律顧問.

## 參考來源

本頁的三項前提, 表格內容與建議步驟是整理者依本手冊各章整理的判斷框架 (信心: 中, 屬推論), 不是市場統計. 頁內可查證的外部事實只有以下兩項.

- **開放權重模型與雲端旗艦模型有能力差距**: Epoch AI 是追蹤 AI 模型能力與算力趨勢的研究機構, 該機構 2026-05-29 的資料洞察指出, 最強的開放權重模型平均落後封閉前沿模型約 4 個月, 以 Epoch Capabilities Index (ECI) 計約 8 點 (自 2026 年 1 月起統計). 該指數是通用能力的綜合指標, 不代表讀者自己的任務, 因此本頁建議用自己的題目實測. [Epoch AI: 開放與封閉模型的能力差距](https://epoch.ai/data-insights/open-closed-eci-gap)
- **2026 年已知事件多出在推論引擎之上的中介層**: CISA Known Exploited Vulnerabilities (KEV) 目錄是美國網路安全暨基礎設施安全局 (CISA) 維護的「已確認遭實際利用的漏洞」清單. 該目錄 (catalogVersion 2026.10.23) 列有 LiteLLM 3 筆 (CVE-2026-42208, CVE-2026-42271, CVE-2026-59822), Langflow 6 筆, n8n 1 筆 (CVE-2025-68613). LiteLLM 是統一轉送模型呼叫並管理金鑰的閘道; Langflow 是以拖拉方塊組出 AI 應用流程的低程式碼平台; n8n 是串接各系統, 依排程或事件自動執行工作的流程自動化平台. 這些是已知被利用的漏洞實例, 不是事件的完整統計; 「多出在」是整理者對這些實例的歸納 (信心: 中, 推論). 逐項來源與 Flowise 的紀錄見[架構地圖](/start/map)的參考來源. [CISA: Known Exploited Vulnerabilities 目錄 (JSON)](https://www.cisa.gov/sites/default/files/feeds/known_exploited_vulnerabilities.json)

其餘敘述的依據在各章:

- 「顯示記憶體或統一記憶體常比運算速度更常決定能跑哪些模型」: 見 [K2](/know/k2-quantization) 的算式與 [K3](/know/k3-hardware).

- 「三項沒有同時成立時, 雲端 API 或混合做法通常較省事」: 整理者推論 (信心: 中), 無外部統計.
