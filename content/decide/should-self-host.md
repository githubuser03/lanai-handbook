**結論**: 依序回答四個問題即可得到初步方向. 結果是整理者的建議 (信心: 中, 屬推論), 不是唯一答案.

## 決策樹

決策樹是一連串是非題, 每一題的答案決定下一題, 最後落到一個建議結果. 從 Q1 開始, 依箭頭往下走即可.

```
Q1 資料是否因內部規範或合約, 必須留在自己的環境內?
 |-- 是 --> Q2
 |-- 否 --> Q3

Q2 有人能每週維運 (安全公告, 備份, 升級)?
 |-- 是 --> 結果 C: 地端 (先以 30 天 PoC 確認模型在自己的任務上夠用, 再從最小組合起步)
 |-- 否 --> 結果 D: 暫緩, 先補維運人力, 或評估廠商託管的私有部署

Q3 用量是否穩定且偏高 (長期攤提硬體有意義)?
 |-- 是 --> Q4
 |-- 否 --> 結果 A: 雲端 API

Q4 開放權重模型在自己的任務上, 實測是否夠用?
 |-- 是, 且有人維運 --> 結果 B: 混合 (敏感或高用量任務地端, 其餘雲端)
 |-- 是, 但沒人維運 --> 結果 A: 雲端 API
 |-- 否或不確定 --> 結果 D: 先做 30 天 PoC 實測
```

## 各結果的說明

四個結果中, A 是全部使用雲端服務, C 是全部在自己的環境執行, B 介於兩者之間, D 則是先補足條件或先試做再決定. 試做在本手冊稱為 PoC (Proof of Concept, 概念驗證), 指正式投資前的小規模驗證.

| 結果 | 建議做法 | 下一步 |
|---|---|---|
| A 雲端 API | 以企業方案採購, 並確認供應商的資料處理條款 | 條款判讀請洽法律顧問 |
| B 混合 | 地端處理敏感或高用量任務, 其餘走雲端; 閘道的需求見 [M5.1 節](/build/m5-gateway-identity) | 先做 PoC, 再決定是否加閘道 |
| C 地端 | 先以 PoC 確認模型能力 (同 Q4 的實測), 再採最小組合起步, 逐步加層 | [30 天 PoC 計畫](/decide/poc-30days), [「組裝總覽」](/build/overview)與 [K6](/know/k6-security) |
| D 暫緩 | 補足維運人力, 或先用 PoC 取得實測資料 | [30 天 PoC 計畫](/decide/poc-30days) |

## 使用提醒

- Q4 的「夠用」應以自己的 20 至 50 題實測判斷, 不以排行榜分數替代 (見 [M4.3 節](/build/m4-retrieval)與 [M6](/build/m6-observability)).
- Q2 的「有人維運」指有具名的人, 每週實際執行; 只在組織圖上有職稱不算.
- 本決策樹未涵蓋法規與契約細節, Q1 的答案請由法務或資安負責人確認.
