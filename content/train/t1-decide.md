# T1 是否需要訓練的判斷

::: info 本章屬性
- 等級: ○ 依情境
- 狀態: 可閱讀 (部分資料待核對)
- 資料基準日: 2026-10-27
- 待查證: 「先提示, 再檢索, 最後才微調」的順序與決策流程為整理者歸納 (推論); 訓練時間依資料量, 硬體與設定差異很大, 本章不給數字, 需以小規模試跑實測; 顯示記憶體數字為 Unsloth 與 LLaMA-Factory 官方標示的最低值或估計值, 未實機驗證; 文中的類比為整理者所寫, 不代表技術上完全等同
:::

**結論**: 多數需求用提示與檢索就能解決, 微調應放在最後. 提示是把要求寫清楚, 檢索是讓模型先查自己的文件 (見 [M4](/build/m4-retrieval)), 兩者都不必重新訓練模型. 微調適合改變模型的「做法」, 例如固定的回答格式, 特定的語氣或分類規則; 若要讓模型「知道」新的事實, 檢索通常比微調可靠 (推論, 信心: 中). 決定微調之前, 先用 [M6](/build/m6-observability) 的測試集量出提示與檢索的成績, 有了基準線, 才知道微調是否值得.

::: tip 本章常見名詞
| 詞 | 意思 |
|---|---|
| 提示 (prompt) | 送給模型的指示與問題 |
| 檢索增強生成 (RAG) | 回答前先從自己的文件找出相關段落, 再交給模型參考, 見 M4 |
| 微調 (fine-tuning) | 拿自己的資料, 在現成模型上再訓練一次 |
| 監督式微調 (SFT) | 用「問題與標準答案」成對的資料微調, 是最常見的微調方式 |
| 訓練集, 驗證集, 測試集 | 分別用來訓練, 訓練途中檢查, 以及訓練後驗收的三份資料, 彼此不可重疊 |
| LoRA 與 QLoRA | 只訓練一小組附加參數的微調方法, 原理見 [T2](/train/t2-finetune) |
| 顯示記憶體 (VRAM) | 顯示卡專用的記憶體, 決定能微調多大的模型 |

完整詞彙見[術語對照](/ref/glossary).
:::

## T1.1 提示, 檢索與微調的選擇

三種做法的差別, 可以想成帶新同事: 提示是把工作交代清楚, 檢索是給一份手冊讓對方隨時查, 微調則是送去受訓. 交代清楚就能做好的事, 不必送去受訓; 需要查資料的事, 給手冊比要求背下來可靠. 三者投入的資料與算力依序增加 (推論, 信心: 中).

OpenAI 的模型最佳化指南把流程排成: 先寫評測, 量出目前的表現作為基準線, 再調整提示; 指南表示, 調整提示的過程「可能就足以」得到很好的結果, 微調則是部分情境才需要 (來源: OpenAI 文件 Model optimization). 同一份指南列出微調相對於只用提示的好處: 能提供比單次請求上下文更多的範例, 提示可以縮短以降低成本與延遲, 可以讓模型穩定以特定格式回答, 也可以把小模型訓練成在特定工作上表現接近大模型 (來源同上). 這份指南也註明 OpenAI 正逐步結束其微調平台; 雲端微調服務本身也會變動, 這是考慮地端微調的原因之一 (來源同上).

微調比較擅長改變「怎麼回答」, 不擅長灌入新知識. LIMA 論文只用 1,000 筆精選的問答, 微調一個 65B 參數的模型, 就得到與部分商用模型相當的人工評比結果; 作者據此主張, 大型語言模型幾乎所有的知識都在預訓練階段學到, 微調主要教的是回答的格式與風格 (來源: Zhou 等人, LIMA: Less Is More for Alignment, 2023). 因此, 內部規章, 產品資料這類會更新的事實, 適合放進檢索; 公司慣用的報告格式, 固定的分類規則, 才適合考慮微調 (推論, 信心: 中).

**決策流程** (整理者歸納, 推論, 信心: 中):

```
[需求] 先用 M6 測試集量出目前的成績 (基準線)
   |
   v
調整提示 (把要求, 範例, 格式寫清楚) --> 達標 --> 結束
   | 未達標
   v
問題在「不知道某些事實」? --是--> 加上檢索 (M4) --> 達標 --> 結束
   | 否, 問題在格式, 語氣或判斷規則           | 未達標
   v                                        v
備妥 1,000 筆以上的高品質範例? --否--> 先整理資料 (T1.2), 或回到提示
   | 是
   v
估算顯示記憶體與成本 (T1.3) --> 可行 --> 微調 (T2), 用同一份測試集驗收
```

「1,000 筆」取自 LIMA 的設定, 是說明量級的參考, 不是保證有效的門檻; 實際需要的筆數依工作而定 (推論, 信心: 低).

## T1.2 資料準備與品質檢查

微調資料的好壞, 直接決定微調後的模型像不像預期. 可以想成編寫受訓教材: 教材裡的錯誤示範, 學員也會照著學. 資料準備要回答四個問題: 要多少, 長什麼樣子, 品質怎麼檢查, 機密資料怎麼處理.

**資料量**: LIMA 的結果顯示, 品質比數量重要, 1,000 筆精選範例就能改變模型的回答風格 (來源: LIMA 論文). 若筆數不多, 先把每一筆做對, 比大量蒐集良莠不齊的資料更有效 (推論, 信心: 中).

**格式**: 微調工具多半讀取 JSONL 檔, 也就是每一行一筆 JSON 資料的文字檔. 以 MLX LM (在 Apple Silicon 上執行與微調模型的套件, 見 T2) 為例, 支援 `chat` (多輪對話), `tools` (工具呼叫), `completions` (提示與回答) 與 `text` (純文字) 四種格式; 資料目錄中必須有 `train.jsonl`, `valid.jsonl` 為選配, 有的話訓練途中會定期回報驗證損失 (來源: MLX LM 文件 LORA.md). 其他工具的格式各有規定, 見 [T2](/train/t2-finetune).

**品質檢查** (整理者建議, 推論, 信心: 中):

- [ ] 每筆答案都經過熟悉業務的人核對, 沒有錯誤事實
- [ ] 同類問題的答案格式一致, 不會一筆用條列, 一筆用段落
- [ ] 刪除重複與幾乎重複的範例
- [ ] 抽出一部分當驗證集, 並保留 M6 的測試集不放進訓練資料; 測試題若混進訓練資料, 驗收分數會偏高, 這種情形稱為資料汙染 (見 [K5](/know/k5-tools-agents))

**個人資料與機密資料**: 模型可能記住部分訓練資料, 並在回答中重現 (見 [K1.7 節](/know/k1-basics)). 因此, 個人資料與機密資料要在進入訓練資料前就移除或遮蔽, 不能指望訓練後再過濾. Google 在 Gemma 3 的模型卡中說明, 預訓練資料以自動化方法過濾了部分個人資訊與其他敏感資料 (來源: Gemma 3 模型卡); 自行微調時也應比照, 在資料準備階段做過濾 (推論, 信心: 中). 微調後的模型檔本身也應視為與訓練資料同等級的機密, 依 [M3](/build/m3-model-intake) 的方式管理存放權限 (推論, 信心: 中).

## T1.3 成本與時間估算

微調的成本主要是顯示記憶體與時間. 顯示記憶體決定「能不能做」, 時間決定「要等多久, 電費多少」. 可以想成搬家: 卡車容量 (顯示記憶體) 不夠, 家具就裝不下; 容量夠了, 才談要跑幾趟 (時間).

**顯示記憶體**: Unsloth (以較少顯示記憶體微調模型的訓練框架, 見 T2) 官方文件列出各模型大小的最低需求, 並說明這些是絕對最低值, 部分模型需要更多 (來源: Unsloth 文件 Unsloth Requirements):

| 模型參數量 | QLoRA (4 位元) | LoRA (16 位元) |
|---|---|---|
| 3B | 3.5GB | 8GB |
| 8B | 6GB | 22GB |
| 14B | 8.5GB | 33GB |
| 27B | 22GB | 64GB |
| 32B | 26GB | 76GB |
| 70B | 41GB | 164GB |

LLaMA-Factory (提供網頁介面的微調框架, 見 T2) 的估計表另列出 7B 模型的全參數微調需要 120GB, 16 位元 LoRA 需要 16GB, 4 位元 QLoRA 需要 6GB, 並標示為估計值 (來源: LLaMA-Factory GitHub README). 兩份資料的 LoRA 數字不同, 原因是計算條件不同, 實際用量以試跑為準 (推論, 信心: 中). 對照 [K3](/know/k3-hardware) 的硬體等級, 只有一張消費級顯示卡時, QLoRA 是較實際的選擇 (推論, 信心: 中). Unsloth 文件也提醒, 記憶體不足的錯誤常是批次大小設得太大, 建議先設為 1 至 3 (來源: Unsloth 文件).

**時間**: 訓練時間取決於資料的 token 數, 訓練回合數 (epoch, 整份資料完整走過一次稱為一個回合), 模型大小與顯示卡, 公開資料無法給出適用各環境的數字. 建議先抽 5% 至 10% 的資料試跑一個回合, 記錄耗時, 再依比例推估完整訓練的時間 (整理者建議, 推論, 信心: 中).

**與雲端 API 的比較**: 沿用[成本試算表](/decide/tco)的框架, 在自架年成本中加入下列微調專屬項目:

| 成本類別 | 公式 | 填入數字 |
|---|---|---|
| 資料整理人時 | 整理與核對的小時數 x 時薪 | |
| 訓練電費 | 試跑推估的訓練小時 x 平均功耗 (kW) x 電價 (元/度) x 每年重訓次數 | |
| 驗收人時 | 每次以 M6 測試集比較與人工判讀的小時數 x 時薪 x 每年重訓次數 | |
| 重訓頻率 | 基底模型改版, 或業務規則變更時都要重訓; 依過去一年的變更次數估計 | |

微調的成本不是一次性的. 基底模型每次改版, 附加的 LoRA 參數通常要重新訓練 (推論, 信心: 中); 若業務規則每季變動, 檢索只要更新文件, 微調則要重做一輪資料與驗收. 這是「事實放檢索, 做法才微調」的另一個理由.
