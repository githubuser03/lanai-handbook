第 13 章 工作流程, 代理與 MCP ​

本章屬性

  • 等級: ◇ 進階
  • 狀態: 草稿, 待人工審閱
  • 資料基準日: 2026-10-26
  • 待查證: BFCL 分數取自彙整站 benchmarklist.com, 應改連官方排行榜; MCP 授權規範細節未逐條驗證

結論: 多數情境不需要代理框架. 以「固定步驟的工作流程程式碼 + 每步一次函式呼叫 + 程式端驗證」取得的可靠度最高 (信心: 中高). MCP 與 LangGraph 都值得了解, 但屬於符合特定條件才用的元件.

13.1 先寫工作流程, 再考慮代理 ​

小模型「選對函式, 填對參數」的單步準確率約 80% 至 88%, 但多輪任務只有約 30% 至 42%.

讓 8B 模型自主串接 5 步以上的工具, 失敗是常態 (信心: 中高). 另有一篇論文 (arXiv 2608.22472) 顯示, 改用「指令遵循式」函式呼叫格式, 可讓 Qwen3-4B 與 8B 在 BFCL 子集提升到 90% 以上, 表示提示格式與流程設計的影響可能大於換框架 (信心: 中).

13.2 函式呼叫與 MCP 的取捨 ​

MCP (Model Context Protocol) 最新規格是 2026-07-28 版, 核心改為無狀態, 取消 initialize 交握與 Mcp-Session-Id 標頭, 並新增正式的棄用政策 (12 個月棄用期). 美國 NSA 於 2026-06-02 發布 MCP 安全設計指引.

情境建議
自己撰寫的單一應用, 工具不超過 3 至 5 個, 只有一個客戶端直接用函式呼叫
同一組工具要給多個客戶端共用 (Open WebUI, IDE, 桌面助理)使用 MCP
要使用信譽良好的現成伺服器使用 MCP, 並依 13.3 審核
低階硬體的初階讀者不建議作為入門步驟

不建議初階讀者的理由有三: 小模型多輪工具呼叫可靠度低; 每個 MCP 伺服器都是以使用者權限執行的程式; 一般函式呼叫就能完成同樣的事 (信心: 中高). 手冊範例須標註所依據的 MCP 規格版本.

13.3 MCP 伺服器的審核與沙箱化 ​

已公開的事件顯示風險真實存在:

日期事件來源

2025-06CVE-2025-49596, 官方 MCP Inspector 缺乏驗證, 可經惡意網頁執行程式碼 (CVSS 9.4)The Hacker News, Vulnerable MCP Project
2025-07CVE-2025-6514, mcp-remote 經惡意伺服器注入作業系統命令 (CVSS 9.6), 0.1.16 修補JFrog, The Hacker News
2025-09postmark-mcp npm 套件後門, 首例實際環境中的惡意 MCP 伺服器pipelab.org
2026-06Miasma 蠕蟲在 73 個 GitHub 儲存庫植入惡意 MCP 設定檔, IDE 開啟專案即自動執行Cloud Security Alliance

另有研究 "MCP at First Glance" (arXiv:2506.13538) 分析 1,899 個開源 MCP 伺服器, 摘要指出 7.2% 含一般漏洞, 5.5% 有 MCP 特有的工具投毒.

審核做法 (信心: 中高):

  1. 來源: 只用官方或知名組織維護的伺服器, 確認套件發行者與儲存庫一致.
  2. 鎖定版本: 固定版本號與雜湊, 不用 npx -y 拉最新版; 工具描述變更時重新審核, 以防 rug pull.
  3. 權限最小化: 檔案系統伺服器只開放單一資料夾; 資料庫伺服器使用唯讀帳號.
  4. 沙箱化: stdio 伺服器放進容器 (無網路或限制對外連線, 非 root, 唯讀根檔案系統).
  5. 不讓專案自動載入 MCP 設定: 關閉 IDE 的自動信任.
  6. MCP 閘道: 對初階讀者過度, 且 LiteLLM 的 MCP 路由本身就出過多個 CVE.

13.4 LangGraph 程式庫與低程式碼平台的風險 ​

LangGraph ​

  • 程式庫採 MIT 授權, 可完全地端執行, 無商業限制.
  • LangGraph Platform 已改名為 LangSmith Deployment. 依 LangChain 官方 CLI 文件, langgraph up 啟動的 Agent Server 在正式環境需要授權金鑰.
  • 因此本手冊建議把 LangGraph 當函式庫, 嵌入自己的 FastAPI 或腳本 (信心: 高).
  • 需要理解狀態圖, 檢查點與節點等概念, 對初階讀者偏陡 (信心: 中, 屬推論).

低程式碼平台 ​

Langflow, n8n, Flowise 這類平台設計上就會執行使用者提供的程式碼, 預設以高權限執行, 又保存所有憑證, 因此 2026 年已知被利用的漏洞最多.

對初階讀者的建議 (信心: 高):

  • 若要學習, 只在本機或 VPN 內使用.
  • 不直接對網際網路開放.
  • 自動更新至最新修補版.
  • 不把正式環境金鑰放進去.
  • 稱 Dify 為「原始碼公開」, 不稱「開源」.
