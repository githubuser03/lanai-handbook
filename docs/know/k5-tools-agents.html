K5 工具呼叫, MCP 與代理 ​

本章屬性

  • 等級: ○ 依情境
  • 狀態: 可閱讀 (部分資料待核對)
  • 待查證: K5.4 節的 BFCL 分數取自官方排行榜提供的資料檔 data_overall.csv (頁面標示最後更新 2026-04-12), 模型範例已更換, 數字須對照官方排行榜與各模型卡; Nemotron 一列為模型卡自報的 BFCL v3 分數, 未經排行榜重跑; K5.4 節引用的 arXiv 2608.22472 只讀了摘要, 摘要未列具體數字; K5.5 節的 MCP 規格版本, NSA 指引日期本輪未重新核對; K5.3 節的題目配置與判定方式為整理者建議, 未實測
  • 資料基準日: 2026-10-26

結論: 模型本身不會「動手」, 它只會輸出「要呼叫哪個工具, 帶什麼參數」, 由程式去執行. 多數情境不需要代理框架, 以「固定步驟的工作流程程式碼 + 每步一次函式呼叫 + 程式端驗證」取得的可靠度最高 (信心: 中高). MCP 是讓多個客戶端共用同一組工具的標準協定, 代理則是讓模型自己決定下一步; 兩者都屬於符合特定條件才用的元件.

K5.1 單步準確率與多輪可靠度的差別 ​

工具呼叫的評測分成兩種能力, 兩者的分數差距很大, 不能互相代替.

單步: 給模型一段使用者請求與一組函式定義, 看模型是否選對函式, 參數名稱與型別是否正確. BFCL 主要以抽象語法樹 (AST) 解析模型輸出, 比對函式名稱, 參數, 型別與值; V1 另有實際執行函式的類別, 兩者互補 (來源: BFCL V1 部落格). 這一類又分成兩組題目:

  • 非即時 (Non-Live): 研究團隊自行撰寫的題目, 分為 simple, multiple, parallel, parallel multiple 四個子項, 分別測試「單一函式」「從多個函式中選一個」「一次呼叫多個」與兩者的組合.
  • 即時 (Live): 使用者貢獻的真實函式與請求, 用來降低資料汙染 (data contamination) 與偏差的影響; 同一模型在 V1 與 Live 題目的分數落差很大時, 可能表示模型看過舊題目 (來源: BFCL V2 部落格).
  • 幻覺量測 (Hallucination): 給模型不相關的函式, 看模型是否懂得「不呼叫」.

多輪: 使用者與模型往返多回合, 模型要記得前面的內容, 並把一個函式的輸出當作下一個函式的輸入. BFCL V3 在每一回合結束時做兩種檢查, 每一回合都通過才算答對 (來源: BFCL V3 部落格):

  • 狀態檢查: 比對後端系統的最終狀態與標準答案, 用於寫入與刪除類動作.
  • 回應檢查: 比對模型的呼叫路徑是否包含最短可行路徑, 用於唯讀請求; 多呼叫幾次不扣分.
  • 單一回合超過 20 步仍未結束, 直接判錯.

多輪類別包含四種情境: 資訊齊全的基本題, 缺少必要參數 (模型應該發問而不是猜測), 缺少可用函式 (模型應該察覺沒有合適的工具), 以及長上下文 (大量無關資料混在其中) (來源: BFCL V3 部落格). 官方部落格列出的典型失敗包含: 沒有先查狀態就直接動作, 重複登入已經登入的服務, 以及陷入重複呼叫的迴圈.

BFCL V4 新增的代理類別: V4 加入網路搜尋 (100 題人工撰寫的多步推理問題, 搭配搜尋與擷取網頁兩種工具, 並隨機模擬 503 與逾時) 與記憶兩項代理評測; 另有格式敏感度 (format sensitivity) 測試, 只適用於 Prompt 模式的模型, 而且不計入總分 (來源: BFCL V4 部落格, BFCL 排行榜頁).

單步與多輪的落差可以用簡單的估算理解: 若每一步成功率都是 87%, 而且各步彼此獨立, 連續 5 步都成功的機率約為 0.87 的 5 次方, 約 50%. 實際任務中各步並不獨立, 前一步的錯誤會使後一步更難, 因此這個估算只用來說明方向 (推論, 信心: 中). 這也是 K5.4 節建議「每步一次函式呼叫, 由程式串接」的原因.

K5.2 BFCL 分數的讀法與限制 ​

官方排行榜位於 gorilla.cs.berkeley.edu/leaderboard.html. 讀分數時, 先確認下列四件事.

1. 總分的權重偏重代理與多輪: BFCL V4 的總分公式為代理 40%, 多輪 30%, 即時 10%, 非即時 10%, 幻覺量測 10%; 代理一項由網路搜尋與記憶等權平均 (來源: BFCL V4 部落格). 因此一個單步準確率超過 80% 的小模型, 總分仍可能只有 30% 左右, 如 K5.4 節的表格所示. 讀者若只打算讓模型做單步呼叫, 應該看非即時與即時兩欄, 而不是總分; 打算讓模型自主串接多步, 才需要看多輪與代理兩欄 (推論, 信心: 高).

2. 評測模式: 排行榜把模型分成 FC 與 Prompt 兩種模式. FC 代表模型原生支援函式呼叫, Prompt 代表以一般文字生成模擬函式呼叫 (來源: BFCL 排行榜頁). 同一個模型在兩種模式下的分數不同, 比較時要對齊模式. 地端部署時, FC 模式能否發揮, 還取決於推論伺服器的 tool-call parser 與 chat template 是否和模型相符 (見 M1).

3. 版本與資料日期: 官方頁面標示的最後更新日與評測程式版本 (commit 與 PyPI 套件 bfcl-eval 的版本), 是判斷分數是否可以互相比較的依據; 總分組成在 V3 與 V4 之間已經改變, V3 部落格也註明其總分組成已過時 (來源: BFCL 排行榜頁, BFCL V3 部落格). 彙整站轉載的分數可能來自不同時間點, 也可能混用不同版本的欄位. K5.4 節的表格取自官方排行榜網站提供的資料檔 (data_overall.csv), 資料版本須與頁面標示的最後更新日對照 (待核對).

4. 模型卡自報分數: 模型發布者在模型卡上自報的 BFCL 分數, 可能使用不同的評測版本, 子集或提示格式, 沒有經過排行榜團隊重跑. 這類分數只能當作發布者的宣稱, 不應與排行榜分數放在同一欄比較 (信心: 高). K5.4 節的 NVIDIA-Nemotron-Nano-9B-v2 一列即屬此類, 該列為 BFCL v3 分數, 與其他列的 V4 版本不同.

評測本身的限制: 官方部落格自己列出的限制包含: 網路搜尋只有 100 題; 部分模型不使用工具, 直接以訓練資料作答, 仍可能答對; 答案以正規化後的精確比對評分, 標準嚴格 (來源: BFCL V4 部落格). 除此之外, 排行榜的函式與請求都是通用情境, 不是讀者自己的工具與繁體中文請求; 地端執行的量化版本, 也可能與排行榜評測的版本不同 (推論, 信心: 中). 因此排行榜適合用來縮小候選範圍, 最後仍須用 K5.3 節的方法實測.

K5.3 用自己的任務做 20 題實測 ​

排行榜回答「這個模型一般表現如何」, 實測回答「這個模型能不能用在自己的工具上」. 建議在選定候選模型後, 以自己的工具定義與真實請求寫 20 題, 每次換模型, 換量化版本, 換推論伺服器版本或改工具描述時重跑 (信心: 高).

題目配置: 下表的配置參考 BFCL 的分類方式, 題數為建議值, 可依自己的工具數量調整 (推論).

類型題數期望行為對應 BFCL 類別
單一工具6選對工具, 必要參數齊全, 型別正確非即時 simple
相似工具擇一4從名稱或用途相近的工具中選對一個非即時 multiple
不應呼叫3請求與工具無關時, 直接回答或拒絕, 不呼叫工具幻覺量測
缺少參數2必要資訊不足時發問, 不自行編造參數多輪 missing parameter
兩到三步串接3依序呼叫, 並把前一步的輸出帶入下一步多輪 base
含不可信內容2請求附帶的文件內藏有指令時, 不照著做 (見 K5.6)無直接對應

每題記錄的欄位: 題號, 使用者請求 (以真實工作語句撰寫, 含繁體中文與常見縮寫), 提供給模型的工具清單, 期望的工具名稱與參數, 判定方式. 下面是一題的記錄範例, 格式為本手冊自訂, 不是特定工具的設定語法:

json
{
  "id": "tool-07",
  "request": "查一下昨天 10.0.5.23 有沒有登入失敗的紀錄",
  "tools": ["siem.query", "ticket.create", "host.lookup"],
  "expect": {
    "tool": "siem.query",
    "args": { "src_ip": "10.0.5.23", "event": "login_failure", "range": "1d" }
  },
  "check": "工具名稱完全相同; src_ip 完全相同; range 允許 1d 或 24h"
}

判定方式: 參考 BFCL 的做法, 單步題以程式比對工具名稱與參數 (相當於 AST 比對), 不靠人工目視; 串接題另外檢查執行後的系統狀態 (例如測試環境中是否真的建立一張 ticket), 寫入類動作一律在測試環境執行 (推論, 信心: 中高). 同一題的模型輸出每次可能不同, 建議每題至少跑 3 次, 並固定溫度等取樣參數, 以「3 次全對」與「至少 1 次對」兩個比率分別記錄 (推論).

併入 M6 測試集: 這 20 題就是 M6.1 節測試集中「工具呼叫題」一類, 與日常任務題, 檢索問答題放在同一份測試集, 以同一套流程執行與比較 (見 M6). 結果出現退步時, 先檢查 tool-call parser, chat template 與工具描述是否有變動, 再考慮換模型.

K5.5 函式呼叫與 MCP 的取捨 ​

MCP (Model Context Protocol) 最新規格是 2026-07-28 版, 核心改為無狀態, 取消 initialize 交握與 Mcp-Session-Id 標頭, 並新增正式的棄用政策 (12 個月棄用期). 美國 NSA 於 2026-06-02 發布 MCP 安全設計指引.

情境建議
自己撰寫的單一應用, 工具不超過 3 至 5 個, 只有一個客戶端直接用函式呼叫
同一組工具要給多個客戶端共用 (Open WebUI, IDE, 桌面助理)使用 MCP
要使用信譽良好的現成伺服器使用 MCP, 並依 M7.1 節審核
低階硬體的初階讀者不建議列為入門步驟

不建議初階讀者的理由有三: 小模型多輪工具呼叫可靠度低; 每個 MCP 伺服器都是以使用者權限執行的程式; 一般函式呼叫就能完成同樣的事 (信心: 中高). 手冊範例須標註所依據的 MCP 規格版本.

K5.6 代理, 政策與隔離的基本概念 ​

本節是 M8 代理與治理的底層知識. 核心觀念只有一句: 模型的輸出不能當作授權, 每個會改變系統狀態的動作, 都要由模型以外的確定性規則再判定一次 (信心: 高).

提示注入 (prompt injection) ​

OWASP 將提示注入定義為「使用者的提示以非預期的方式改變 LLM 的行為或輸出」, 並分為兩種 (來源: OWASP GenAI, LLM01:2025):

  • 直接注入: 使用者自己輸入的內容改變模型行為, 可能是刻意的, 也可能是無意的.
  • 間接注入: 模型讀取網頁, 檔案, 郵件, log 等外部內容時, 內容中夾帶的指令影響模型. 人看不到的文字, 只要模型會解析, 一樣有效.

OWASP 指出, 由於模型的隨機特性, 目前不清楚是否存在萬無一失的防範方法. 該頁列出的因應方向包含: 在系統提示中界定模型角色與限制; 規定輸出格式, 並以確定性程式碼檢查輸出; 應用程式使用自己的 API 憑證, 特權功能在程式碼中執行, 只給最小權限; 高風險動作需要人工核准; 明確區隔並標示不可信的外部內容; 定期做對抗測試 (來源: OWASP GenAI, LLM01:2025). 這些方向的共同點是「假設注入會成功, 限制成功之後能造成的影響」, 本手冊 M7 與 M8 的設計都依此展開. OWASP 其他風險與本手冊的對照見 K6.4 節.

雙 LLM 模式 (隔離模型) ​

Simon Willison 於 2023 年提出雙 LLM 模式 (Dual LLM pattern), 把助理拆成三個角色 (來源: Simon Willison, The Dual LLM pattern):

角色讀什麼能做什麼
特權模型 (Privileged LLM)只讀可信來源, 主要是使用者的指示可以呼叫工具
隔離模型 (Quarantined LLM)讀取不可信內容 (郵件, 網頁等)沒有任何工具, 並假設它隨時可能遭到操控
控制器 (Controller)一般程式, 不是模型觸發兩個模型, 代替特權模型執行動作

控制器把隔離模型的輸出存成變數 (例如 $VAR1), 特權模型只看到變數名稱, 看不到內容. 原文強調, 未經過濾的隔離模型輸出絕對不能轉給特權模型; 唯一的例外是能以固定類別驗證的輸出, 例如分類結果 (來源: 同上). 原文也承認這個模式不是百分之百可靠: 使用者自己複製貼上不可信內容時就會失效, 而且實作複雜, 可能影響使用體驗.

本手冊的隔離模型採用同一個原則, 做法是讓隔離模型只輸出固定欄位的 JSON, 由程式檢查格式與長度後, 才把個別欄位交給 LangGraph (見 M8.3 節). 這個做法擋不住「惡意值放進合法欄位」, 例如在「受影響主機」欄位填入網域控制站的名稱, 因此還需要政策引擎的關鍵資產清單把關 (信心: 中高).

後續研究 CaMeL (arXiv:2503.18813) 從可信的使用者請求中明確抽出控制流程與資料流程, 讓不可信資料無法影響程式流程, 並以 capability 的概念在呼叫工具時套用安全政策, 防止私人資料經未授權的資料流外洩. 論文摘要指出, CaMeL 在 AgentDojo 評測中以可證明的安全性完成 77% 的任務, 未設防的系統為 84% (來源: arXiv:2503.18813 摘要). 這表示「依設計隔離」需要付出一部分任務完成率, 屬於可預期的取捨 (推論, 信心: 中).

政策引擎與人工核准 ​

政策引擎是模型以外的確定性判定點. 代理每次呼叫工具前, 先把「哪個工具, 帶什麼參數, 這次執行已經呼叫幾次」送給政策引擎, 依回傳結果決定執行, 拒絕或轉人工核准. 本手冊使用 OPA (Open Policy Agent), 做法見 M8.2 節. 政策引擎的價值在於它不讀不可信內容, 也不受提示影響, 同一個輸入永遠得到同一個結果 (信心: 高).

人工核准是政策引擎的延伸: 政策判定「需要人看」時, 流程暫停, 等核准者回覆後再繼續. LangGraph 以 interrupt 機制提供這個功能, 見 M8.4 節.

依能否回復分級 (A0 至 A3) ​

動作是否需要人工核准, 依「做錯了能不能回復」決定, 而不是依工具名稱的直覺 (信心: 中高, 屬整理者的設計原則). 下表的 A0 至 A3 是動作分級代號 (A 代表 action).

等級定義範例處理方式
A0 唯讀只讀取, 不改變任何狀態查詢 SIEM, 讀取設定自動執行, 仍受配額限制
A1 內部可自動回復只影響內部, 系統能自動復原建立 ticket, 加註標籤自動執行, 留下紀錄
A2 影響範圍大或對外可見可以回復, 但影響多人或外部看得到隔離主機, 批次修改設定兩個不同模型分別審查, 結果不一致轉人工; 以 canary 方式分批執行
A3 不可回復做了就無法復原刪除資料, 金流, 對外發信, 修改正式環境安全設定一律人工核准

分級寫在政策檔中, 由政策引擎依工具名稱查表, 不讓模型自己申報等級; 不在表內的工具一律拒絕 (推論, 信心: 中高). 實作見 M8.2 與 M8.4 節.
