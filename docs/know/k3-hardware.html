K3 硬體選購 ​

本章屬性

  • 等級: ● 必要
  • 狀態: 可閱讀 (部分資料待核對)
  • 資料基準日: 2026-10-27
  • 待查證: 等級 A 至 F 為整理者設計的分級, 非業界標準; 各等級可跑的模型大小為依 K2 公式的估算, 未實測; 價格見硬體價格頁, 本章不寫價格; K3.4 節的 KV cache 欄位語意與各配置的並行表現為推論, 未實測; 文中的類比為整理者所寫, 不代表技術上完全等同

結論: 預算有限時, 先買「更大的顯示記憶體 (或統一記憶體)」, 再考慮運算速度. 記憶體決定能不能跑, 運算速度只決定跑得多快 (信心: 高).

K3.1 等級 A 至 F 的能力邊界 ​

本手冊把硬體依記憶體多寡分成 A 至 F 六個等級. 記憶體越大, 放得下的模型越大, 等級也越高; 讀者先找出自己的電腦屬於哪一級, 就能知道大致可以跑多大的模型, 以及該從哪一種組合開始.

下表依 K2的公式, 以 4 位元量化中常用的 GGUF Q4_K_M (每參數約 4.8944 位元, 見 K3.4 節) 估算權重: 14B 約 8.6GB, 30B 約 18.4GB, 35B 約 21.4GB, 70B 約 42.8GB (計算值). 權重之外還有 KV cache 與執行開銷, 因此以 K2 的「總需求不超過可用記憶體八成」保守規劃. 結果為推論 (信心: 中), 未實測; 實際能否執行, 還取決於上下文長度與同時使用人數.

K3.2 記憶體優先的選購順序 ​

記憶體容量與頻寬可以想成一座倉庫: 容量是倉庫有多大, 決定貨 (模型) 放不放得下; 頻寬是倉庫大門每秒能進出多少貨. 模型每產生一段文字, 都要從記憶體讀取大量權重, 大門太窄時, 運算單元再快也只能排隊等貨.

  1. 容量: 先確認想跑的模型加 KV cache 放得進去 (K2).
  2. 記憶體頻寬: 產生文字的速度常受記憶體頻寬限制, 而非純運算能力 (信心: 中, 屬一般經驗).
  3. 驅動與軟體支援: Ollama (M1 介紹的推論伺服器) 的 NVIDIA 支援要求運算能力 (compute capability) 5.0 以上, 驅動版本 550 以上; 運算能力 5.0 至 6.2 的舊卡須驅動 570 以上 (來源: Ollama 文件 GPU). AMD 與 Apple 的支援見 M1.4 節.
  4. 電源, 散熱與機殼空間: 高階顯示卡對電源供應器與機殼有要求, 購買前核對規格書 (信心: 高, 屬一般經驗).
  5. 價格時機: DRAM 與 GPU 價格波動大, 以價格頁的查價日期為準, 不憑舊資料決定.

升級既有電腦與另購整機之間, 差異主要在顯示記憶體能否增加. 若現有機器的主機板, 電源與機殼都能容納較大的顯示卡, 升級通常較省 (信心: 低, 屬推論).

K3.3 台灣通路與二手風險 ​

價格與通路資訊放在硬體價格頁, 每筆須有來源與查價日期, 目前該頁尚無內容.

二手顯示卡較便宜, 但外觀看不出過去的使用強度, 也可能遇到規格與標示不符的情況. 以下清單的目的, 是在退換期限內盡量把問題找出來. nvidia-smi 是 NVIDIA 驅動附帶的命令列工具, 可以列出顯示卡型號, 記憶體容量, 溫度與使用率.

購買二手顯示卡時, 建議逐項檢查 (信心: 中, 屬一般經驗):

  • [ ] 收到後立即用 nvidia-smi 確認型號與顯示記憶體容量與賣方標示相符.
  • [ ] 連續跑一段時間的推論或壓力測試, 觀察溫度與是否降頻或當機.
  • [ ] 確認保固剩餘期間與可否退換.
  • [ ] 確認驅動仍在支援清單內 (見上述 Ollama GPU 支援條件).
  • [ ] 外觀與風扇狀況, 是否有拆修痕跡.
  • [ ] 避免來源不明且價格明顯低於市場的商品.

K3.4 範例: 同時常駐 3 個 30B 至 35B 級模型 ​

結論: 單機要同時常駐 3 個約 35B 的模型, 目前最穩的選擇是 1 張 96GB 的 NVIDIA RTX PRO 6000 搭配 4 位元量化, 或 2 張同款卡搭配 FP8. 統一記憶體機種 (NVIDIA GB10 系列, AMD Strix Halo, Apple Mac Studio) 容量夠, 但記憶體頻寬較低, 較適合低併發; 多人同時使用時, 頻寬與推論軟體的成熟度比容量更常成為瓶頸 (信心: 中, 屬推論). 預算區間見硬體價格頁, 硬體價格頁引用 TrendForce 2026-09-30 的報導, 2026 年第 4 季 DRAM 合約價持續上漲, 價格頁所列的多款 GPU 與整機在官方通路標示缺貨, 採購前請以當月報價為準.

這個範例對應架構地圖的情境: LiteLLM (模型閘道, 見 M5) 同時接雲端模型與地端模型, 地端常駐 3 個約 35B 的模型, 推論伺服器的做法見 M1.11 節, 路由與備援見 M5.5 節.

先決定三件事 ​

挑硬體之前, 要先決定要跑什麼樣的模型, 用什麼精度, 以及同時給多少人用. 這三件事決定需要多少記憶體, 記憶體的需求再決定買哪一種硬體.

決定選項對硬體的影響
模型型態密集 (dense) 或 MoE (混合專家)MoE 每個 token 只讀取啟用的參數 (例如總參數 30B 左右, 啟用 3B 至 4B), 對頻寬的需求低很多; 但權重仍須全部放進記憶體, 容量以總參數計
精度BF16, FP8, 4 位元每降一級, 權重約減半; 4 位元的品質損失依模型與任務而異, 上線前須用自己的測試集比較 (M6)
並行與上下文同時多少人, 單次多長決定 KV cache 大小, 常是容量的第二大項

權重需要多少記憶體 ​

KV cache 需要多少記憶體 ​

KV cache 是模型邊讀邊做的筆記 (見 K2.3 節), 大小隨上下文長度與同時處理的對話數增加. 這一段用到兩個架構名詞: 分組查詢注意力 (GQA) 讓多個查詢共用同一組 KV heads, 筆記因此變薄; 滑動視窗層只保留最近固定數量 token 的筆記, 像只留最近幾頁, 超過範圍的就丟掉, 所以不會無限增加.

公式 (來源: PagedAttention 論文對 KV cache 大小的計算, 並依分組查詢注意力 GQA 的定義, 把隱藏維度換成 KV heads 與 head_dim 的乘積; 換算為整理者推導): 每個 token 的 KV 位元組數 = 2 x 層數 x KV heads x head_dim x 每個元素的位元組數; 總量 = 該值 x 上下文長度 x 同時處理的序列數.

下表以官方 config.json 的欄位計算 FP16 的 KV cache; 同一表也示範混合注意力架構, 只有完整注意力層的 KV 會隨上下文長度成長.

Gemma 4 的欄位 (global_head_dim, num_global_key_value_heads) 語意為整理者依欄位名稱解讀, 推論引擎實際的配置方式須實測 (信心: 低). 以 Mistral 的數字示範容量: 4 條序列各 32K token, 共 131,072 token, FP16 約 20GiB; 若 vLLM (多人同時使用時採用的推論伺服器, 見 M1) 的 KV cache 改用 FP8 (--kv-cache-dtype fp8), 每個元素 1 位元組, 約減半為 10GiB. vLLM 文件說明, 預設 FP8 在沒有校準時縮放係數為 1.0, 建議用 llm-compressor 校準, 並未提供準確度數字 (來源: vLLM 文件 Quantized KV Cache).

分級依據 ​

A 至 F 是整理者為本手冊設計的分級, 不是業界標準 (推論). A 至 D 對應常見的設備類型: A 無獨立顯示卡的筆電; B 8 至 12GB 顯示記憶體的遊戲電腦; C Apple Silicon Mac; D 16GB 顯示卡. E 與 F 以顯示記憶體 24GB 與 48GB 為分界, 和 Ollama 依顯示記憶體設定預設上下文長度的分界相同 (小於 24GiB, 24 至 48GiB, 48GiB 以上; 來源: Ollama 文件 Context length), 方便讀者對照同一組數字. 各等級的預算區間見價格頁.
