第 11 章 安全與風險控管 ​

本章屬性

  • 等級: ● 必要
  • 狀態: 可閱讀 (部分資料待核對)
  • 資料基準日: 2026-10-26
  • 待查證: 11.3 的沙箱與機密管理工具版本 (gVisor, Podman, SOPS 等) 為訓練資料內資訊, 可能已過時

結論: 地端 AI 最有效的安全措施有四項: 不對網際網路開放, 鎖定版本, 縮小權限, 能還原. 這四項成本低, 且能涵蓋 2026 年已知的主要攻擊途徑.

11.1 網路暴露與存取控制 ​

使用情境做法
單人服務只綁 127.0.0.1
家庭或小團隊只開放內網, 加上介面本身的帳號系統
需要 HTTPS加反向代理: Nginx (內建速率限制) 或 Caddy (自動憑證, 設定較簡單)
10 人以上, 或已有其他自架服務才考慮 Keycloak 或 Authentik 這類 SSO

不要用連接埠轉發把服務直接開到網際網路. SentinelOne 與 Censys 曾觀察到 175,108 台暴露的 Ollama 主機 (研究 1); 2026 年 n8n 於 ShadowServer 2026-02-05 的統計中仍有 24,607 台易受攻擊 (SC Media); Langflow 多個漏洞已有實際利用紀錄 (見第 13 章). 這幾件事屬於同一類問題.

上述存取控制工具的版本未於本輪驗證, 屬訓練資料內資訊, 可能已過時; 分級為研究 2 的推論 (信心: 中高).

11.2 供應鏈: 版本鎖定與映像摘要值 ​

2026-10-21 的 LiteLLM 事件中, v1.107.0, latest, main-latest, main-stable 這些標籤都曾指向惡意映像 (LiteLLM 官方事故報告). 浮動標籤因此不能當作安全依據.

實務做法:

  1. 容器映像以版本號或摘要值 (digest) 鎖定, 不使用 latest.
  2. 記錄每個元件的安裝版本與日期 (見第 19 章).
  3. 升級前先讀發行說明, 並跑一次 promptfoo 測試集 (第 14 章).
  4. 模型權重優先採用 safetensors 格式, 避免載入來源不明的 pickle 檔 (研究 1 已列為風險).
  5. 發現金鑰外洩時, 依「隔離, 重建, 輪替」處理 (第 20 章).

11.3 沙箱與機密管理 ​

沙箱分級 ​

以下分級為依產業慣例的推論 (信心: 中), gVisor, Firecracker, Podman, Docker rootless 的版本與效能未於本輪驗證.

層級做法適用
最低一般容器 + 非 root 使用者 + --network none + 唯讀根檔案系統 + 記憶體與 CPU 上限所有讀者, 成本接近零
中階Podman 或 Docker rootless降低容器逃逸後的權限
進階gVisor (runsc) 提供系統呼叫層隔離多人環境

Firecracker 微型虛擬機需要 KVM, 維運成本高, 不建議手冊讀者使用.

原則: 只要讓模型執行程式碼, 就必須放進沙箱.

機密管理 ​

  • .env 檔 (權限 600, 不進版本控制) 足以應付多數讀者.
  • Docker Compose secrets 是下一階.
  • SOPS 適合用 Git 管理設定的人.
  • HashiCorp Vault 或 OpenBao 對手冊讀者過度.

真正重要的是金鑰外洩後能快速輪替. LiteLLM 兩次事件的官方建議都是「隔離, 重建, 輪替」.

風險本手冊的對應做法

LLM06 無限制資源消耗速率與 token 上限

護欄模型的定位 ​

分類器護欄不建議當作唯一防線, 理由有兩點:

  1. 字元層級手法可繞過偵測. Hackett 等人 (Mindgard 與 Lancaster University, arXiv 2504.11168) 測試 6 套偵測系統, 「Emoji Smuggling」對提示注入與越獄都達到 100% 攻擊成功率; 該研究未測 Prompt Guard 2.
  2. Llama Guard 4 (12B) 依參數量推估 BF16 約需 24GB (推論), 超出硬體等級 A 至 D 的能力.

地端單人環境的主要威脅是間接提示注入, 即模型讀取的文件或網頁內夾帶指令. 比護欄更有效的做法是縮小工具權限, 要求人工確認, 並把程式碼執行放進沙箱 (信心: 中). 多人對外服務時, 才值得加 Prompt Guard 2 22M 這類輕量分類器, 且僅當作「多一層」. LLM Guard (Protect AI) 儲存庫已於 2026-07-09 封存, 不建議新導入.
