第 10 章 閘道與模型切換 ​

本章屬性

  • 等級: ○ 依情境, 符合條件才讀
  • 狀態: 草稿, 待人工審閱
  • 資料基準日: 2026-10-26
  • 待查證: llama-swap 授權 (訓練資料內資訊, 可能已過時); 另有一個 LiteLLM 漏洞據報預定於 2026-10-27 公開, 本章發布前須重新查證

結論: 單機單人不需要閘道. 只有多模型輪替而沒有多人治理需求時, 用 llama-swap 就夠. LiteLLM 有納入評估, 但不列為預設, 原因是一年內兩度成為供應鏈入侵的入口, 且集中保存上游金鑰 (信心: 高).

10.1 何時不需要閘道 ​

Ollama, llama-server 與 LM Studio 都已提供與 OpenAI 相容的 API, 介面可以直接連推論引擎 (信心: 高).

符合下列任兩項, 才考慮加閘道 (信心: 中高):

  1. 3 人以上共用, 需要個別金鑰, 配額或用量紀錄.
  2. 同時混用雲端 API 與地端模型, 需要故障轉移.
  3. 多個應用程式要統一入口.

沒有閘道時, 可用下列做法取代:

  • 介面直連推論引擎
  • 用 llama-swap 處理模型切換
  • 在反向代理 (Caddy) 上做基本驗證與速率限制
  • 使用介面本身的使用者與權限管理 (Open WebUI, LibreChat)

10.2 llama-swap: 多模型輪替 ​

llama-swap 是 Go 撰寫的單一執行檔, 以 YAML 設定, 依請求中的 model 欄位自動啟停 llama-server 或 vLLM. 它相容 OpenAI 與 Anthropic API, 並支援 API 金鑰. 2026 年持續發版, Go 模組在 2026-08-24 仍有更新 (來源: libraries.io 與多篇設定教學彙整; 授權為 MIT 屬訓練資料內資訊, 可能已過時, 請以官方儲存庫核對).

適用情境是一張顯示卡要輪流載入對話模型與嵌入模型, 也就是硬體等級 B, D, E (信心: 中高). 它只做模型切換, 不做多租戶治理, 因此風險等級低於完整閘道.

10.3 LiteLLM 的使用條件與限制 ​

現況 ​

LiteLLM 程式庫採 MIT 授權, 但 enterprise/ 目錄另有授權, SSO 等功能屬企業版 (來源: Maxim AI 與 TechJack Solutions 的比較文). Socket 的 PyPI 頁面顯示 litellm 1.107.0 的週下載量為 22,948,819 次.

2026 年兩次供應鏈事件 ​

日期事件來源
2026-03-24TeamPCP 先入侵 LiteLLM CI/CD 中未鎖定版本的 Trivy 掃描工具, 竊取 PyPI 發布權杖, 再發布含後門的 1.82.7 與 1.82.8Snyk
2026-10-21官方事故報告指出發布流程遭入侵, 惡意 v1.107.0 被推送到 Docker registry 與 PyPI; 惡意 wheel 於 UTC 11:39 至 13:23 在 PyPI 上架; v1.107.0, latest, main-latest, main-stable 標籤都曾指向惡意映像; 惡意程式放在 Python 啟動檔 (cook.pth, sitecustomize.py), 只要 Python 啟動就會執行LiteLLM 官方事故報告, Wiz, Help Net Security

官方建議鎖定 litellm==1.106.2, 或 2026-10-21 之前發布的明確版本 (SOCRadar 轉述). 官方的攻擊鏈分析指出, 起點是 5 月 27 日一個 master key 被提交到公開儲存庫, 之後攻擊者竊得三組 GitHub 權杖. 官方說明企業版私有發行未受影響.

2026 年的 CVE 紀錄見元件版本與安全公告頁. 其中 CVE-2026-42208 為未驗證即可利用的 SQL 注入 (1.81.16 至 1.83.6, 修補於 1.83.7), 來源為 LiteLLM 官方部落格與 Bishop Fox.

判斷 ​

LiteLLM 的問題不在程式碼品質, 而在它是集中保存金鑰的高價值目標. 對單機讀者而言, 它帶來的攻擊面大於效益. 對多人環境而言, 虛擬金鑰與配額是實際需求, 此時須承擔其風險並落實下列措施 (信心: 中高):

  1. 以映像摘要值 (digest) 鎖定版本, 不使用 latest 或 main-stable 標籤.
  2. 只放在內網, 並在反向代理層封鎖管理路徑 (/health/test_connection, MCP 路由).
  3. 不開啟 MCP 功能.
  4. 上游金鑰只給最低權限.
  5. 訂閱 GitHub Security Advisories.
  6. 事先準備好金鑰輪替程序 (見第 20 章).
