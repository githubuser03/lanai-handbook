第 5 章 量化與記憶體需求估算 ​

本章屬性

  • 等級: ● 必要
  • 狀態: 可閱讀 (部分資料待核對)
  • 資料基準日: 2026-10-26
  • 待查證: 4 位元量化的實際位元數與品質損失依格式與模型而異, 本章只給估算方法, 不給單一數字; 範例數字為假設架構的算術結果, 非特定模型

結論: 模型需要的記憶體約等於「權重大小 + 上下文暫存 (KV cache) + 執行開銷」, 三項都能事先估算. 權重大小是「參數量 x 每個參數的位元數 ÷ 8」; 實際下載前, 以模型頁面標示的檔案大小為準 (信心: 高, 屬算術, 開銷比例屬推論).

5.1 量化: 用較低精度換取較小的記憶體占用 ​

量化 (quantization) 是把權重從 16 位元降到 8, 6, 5 或 4 位元等較低精度的做法. 位元數越低, 檔案與記憶體占用越小, 速度通常也更快, 但品質損失越大 (信心: 高).

精度每個參數約占8B 參數模型的權重 (標稱)
16 位元2 位元組約 16GB
8 位元1 位元組約 8GB
4 位元0.5 位元組約 4GB

上表為算術結果 (80 億參數 x 位元組數), 用來示範估算, 非特定模型的實測值. 實際的 4 位元格式因為還存放縮放係數等資料, 檔案通常略大於標稱值 (推論, 信心: 中), 請以下載頁顯示的檔案大小為準.

品質損失怎麼判斷: 損失程度因模型與任務而異, 公開評測多半只涵蓋特定基準, 不能代表你的任務. 較可靠的做法是對同一個模型的兩個量化等級, 各跑一次第 14 章的測試集, 再選擇「品質夠用的最小檔案」(信心: 中高).

檔案格式 ​

格式說明
GGUFllama.cpp 體系使用的單一檔案格式, 量化版本常以此發布
safetensors權重常見的發布格式, 避免了 pickle 檔可能夾帶程式碼的風險 (見第 8.5 節)

Ollama 匯入 GGUF 時不會替你量化; 若要自行量化, 須先用 llama.cpp 的 llama-quantize 等工具處理 (來源: Ollama 文件 Import).

5.2 估算步驟 ​

  1. 取得權重大小: 優先看模型下載頁的檔案大小. 沒有時用「參數量 x 每個參數位元數 ÷ 8」估算.
  2. 加上 KV cache: 見 5.3 節.
  3. 加上執行開銷: 推論引擎本身, 作業系統與介面都需要記憶體. 開銷沒有公開標準, 建議保守規劃, 例如讓總需求不超過可用記憶體的八成 (信心: 低, 屬推論).
  4. 對照可用記憶體: 獨立顯示卡看顯示記憶體; Apple Silicon 看統一記憶體, 但作業系統與其他程式共用同一池.
情況結果
全部放得進顯示記憶體速度最佳
放不下, 部分放到系統記憶體能執行, 但速度明顯變慢 (信心: 高)
連系統記憶體也不足載入失敗或系統嚴重卡頓; 請換較小的模型或較低的量化

混合專家模型 (MoE): 名稱如「30B-A3B」表示總參數約 300 億, 每次推論啟用約 30 億. 記憶體要放下全部權重, 速度則接近較小的模型 (信心: 中高). 估算記憶體時請用總參數.

5.3 上下文長度與 KV cache ​

模型在對話過程中, 會把已處理的內容暫存為 KV cache. 上下文越長, 占用越大, 且與長度成正比.

估算公式 (信心: 高, 屬算術):

KV cache 位元組數 ≈ 2 x 層數 x KV 頭數 x 每頭維度 x 上下文長度 x 每個元素的位元組數

範例 (假設架構, 非特定模型): 32 層, 8 個 KV 頭, 每頭 128 維, 上下文 8,192, 16 位元 (2 位元組):

2 x 32 x 8 x 128 x 8,192 x 2 = 1,073,741,824 位元組, 約 1GiB.

實際模型的層數與頭數, 請從模型卡或設定檔取得.

Ollama 的相關設定 ​

  • 預設上下文為 4096 token; 可用環境變數 OLLAMA_CONTEXT_LENGTH 調整 (來源: Ollama FAQ).
  • 同時處理的請求數 OLLAMA_NUM_PARALLEL 預設為 1; 所需記憶體會隨 OLLAMA_NUM_PARALLEL x OLLAMA_CONTEXT_LENGTH 增加 (來源: Ollama FAQ).

因此記憶體吃緊時, 優先調降上下文長度與同時請求數, 再考慮換更小的模型. 設定方式見第 8.8 節.
