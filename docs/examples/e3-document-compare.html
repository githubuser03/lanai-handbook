E3 合約與法規文件比對 ​

本章屬性

  • 等級: ○ 依情境
  • 狀態: 可閱讀
  • 資料基準日: 2026-10-27
  • 實機驗證: 未進行 (比對腳本與設定依 Python 與 Open WebUI 官方文件整理)

結論: 合約版本比對與法規對照需要里程碑 2 (M0 至 M6). 做法分兩步: 差異由程式找出 (例如 Python 的 difflib), 模型只負責說明每一處差異的意義與分類; 法規對照則把官方公布的條文放進獨立的知識庫, 模型逐條列出內部文件與條文的對應及缺口, 每一項都附條號. 本範例的輸出不是法律意見, 須由法務或法遵專業人員確認後才能使用.

對象: 企業. 需要的模組: M0 至 M6.

情境 ​

法務與法遵人員常做兩種比對工作:

  1. 合約版本比對: 對方送回修改過的合約, 但沒有開啟追蹤修訂, 或只寄來 PDF. 承辦人要逐條找出哪裡改了, 再判斷改動是否影響公司權利義務.
  2. 內部文件對照法規: 法規修正後, 要找出內部辦法有哪些條文須跟著調整, 或檢查一份內部政策是否涵蓋法規要求的事項.

兩種工作都很耗時, 而且合約與內部文件屬機密, 不一定適合交給雲端服務. 本範例的設計前提是: 模型擅長說明與歸類, 但在長篇文件中「找出所有差異」不可靠, 容易漏掉一個數字或一個「不」字 (推論, 信心: 中). 所以找差異交給程式, 判斷交給專業人員, 模型居中整理. 可以想成把新舊兩頁疊在燈箱上, 先由燈箱照出所有不同處, 再請助理在每一處旁邊寫上註記, 最後由律師逐處判斷; 助理只負責寫註記, 不負責找出不同處.

需要的模組 ​

模組里程碑在本範例的用途
M0 基礎環境里程碑 1入口區, 閘道區, 推論區, 稽核區 VM; 比對腳本以批次方式在入口區執行
M1 推論伺服器里程碑 1推論伺服器 vLLM 執行對話模型; 長文件須確認上下文長度足夠
M2 使用者介面與反向代理里程碑 1Open WebUI 是法務與法遵人員提問與上傳文件的對話介面, 只接受內網連線
M3 模型入庫與存放里程碑 2模型經入庫檢查
M4 檢索 (RAG)里程碑 2Docling 把合約與法規的 Word, PDF 解析成純文字 (掃描檔會用到的 OCR 引擎見 M4.1 節); 法規條文獨立成知識庫, 存在 Qdrant 向量庫
M5 模型閘道與身分驗證里程碑 2Keycloak 管理帳號與群組, 限定只有法務, 法遵人員能使用; LiteLLM 是模型呼叫的閘道, 以虛擬金鑰控管用量
M6 可觀測, 稽核與評估里程碑 2已知差異的測試合約與對照題; 呼叫紀錄

流程 ​

A 流程處理合約: 兩版文件先轉成文字並統一格式, 由程式逐條找出差異, 模型只為每一處差異寫說明, 最後由法務人員確認. B 流程處理法規: 官方條文放進只有法遵人員能讀的知識庫, 每次拿一條內部規定去找對應法條, 模型列出對照結果, 程式再檢查模型寫出的條號是否真的存在.

設定要點 ​

以下依 Python 與 Open WebUI 官方文件整理, 未實機驗證.

差異由程式產生 ​

Python 標準函式庫的 difflib 提供序列比對: difflib.unified_diff 輸出統一差異格式, difflib.HtmlDiff 產生左右並排, 標出行內差異的 HTML 表格 (Python 官方文件). 下列簡化範例把新舊兩版依條次逐條比對, 只列出有改動的條次:

python
import difflib

def compare_clauses(old: dict[str, str], new: dict[str, str]):
    """old, new 為 {條次: 條文} 的對照表, 由 Docling 解析結果依條次切開而得."""
    changes = []
    for no in sorted(set(old) | set(new)):
        a, b = old.get(no, ""), new.get(no, "")
        if a != b:
            diff = "\n".join(difflib.unified_diff(
                a.splitlines(), b.splitlines(), lineterm="",
                fromfile=f"舊版 {no}", tofile=f"新版 {no}"))
            changes.append({"clause": no, "old": a, "new": b, "diff": diff})
    return changes

依條次切開的規則 (例如以「第 X 條」為界) 須依自己的合約格式調整. 範例以字串排序條次, 「第10條」會排在「第2條」之前; 條數超過 9 條時, 可改用條次中的數字排序, 差異清單本身不受影響 (整理者以 Python 3.13 執行範例確認). 比對前先統一全半形, 空白與換行, 否則排版差異會淹沒實質差異 (推論, 信心: 高).

合約差異說明的提示範本 ​

這份範本交給模型的只有程式產生的差異清單, 並限定差異類型與輸出欄位, 讓模型只說明, 不另外找差異.

以下是一份合約新舊版本的差異清單, 每一筆含條次, 舊文字與新文字.
請逐筆整理成表格, 欄位為: 條次, 差異類型, 說明, 對我方的可能影響, 建議確認的問題.
差異類型只能是下列之一: 文字修正, 金額或數量變動, 期限變動, 權利義務變動, 責任或賠償變動, 條款新增, 條款刪除.
規則:
1. 只說明清單中的差異, 不要自行找其他差異.
2. 不確定影響時寫「需法務判斷」.
3. 不提供法律意見, 不判斷條款是否有效.

法規對照 ​

  • 條文來源: 法規條文應取自主管機關公布的正式版本, 例如法務部的全國法規資料庫 (建議搜尋關鍵字: 全國法規資料庫 法規名稱), 並在檔名記錄法規名稱與修正日期. 不使用來源不明的整理版. 本流程匯入的是下載後的法規原文檔 (Word 或 PDF), 不依賴特定的開放資料格式.
  • 獨立知識庫: 法規條文與內部文件分開成兩個知識庫, 法規知識庫只授權法遵群組讀取 (權限設計見 E1). 每次法規修正, 刪除舊版並匯入新版.
  • 對照提示範本: 範本要求每個條號都出自檢索到的條文, 範本最後的 CONTEXT 佔位符會換成檢索到的法條; 函式呼叫設定對範本的影響見 P1 的設定要點第 7 點.
以下是一條內部規定, 以及檢索到的法規條文.
請整理成表格: 內部規定 (原文摘錄), 對應法條 (法規名稱, 條號, 修正日期), 對照結果, 說明.
對照結果只能是: 符合, 部分符合, 未涵蓋, 無對應法條.
規則:
1. 每個對應法條都必須出現在參考資料中, 條號照抄, 不得自行推測.
2. 參考資料沒有相關條文時, 填「無對應法條」.
3. 本表僅供專業人員檢視, 不是法律意見.

參考資料:
{{CONTEXT}}
  • 條號存在檢查: 法遵人員把對照表匯出成檔案, 由入口區的批次腳本比對法規原文檔 (就是匯入知識庫的同一批檔案), 找不到的條號標為「待查」. 這一步可以擋下編造的條號, 但無法確認對應是否正確 (推論, 信心: 高). 也可以改寫成 Open WebUI 的 Filter Function, 在回覆送出前自動檢查; 兩種做法的執行位置不同, 效果相同 (推論, 信心: 中).
  • 準確度沒有公開基準: 模型比對長篇合約與法規條文的準確度, 公開資料查無基準 (2026-10-27 查詢). 因此本頁讓程式找出差異, 模型只寫說明, 並以驗收的筆數比對與專業人員確認把關.

差異逐筆送模型, 不整份上傳 ​

差異清單不要以附件上傳到 Open WebUI 對話. Open WebUI 文件說明, 對話中的附件預設以檢索方式處理, 只取回部分內容放進對話, 差異多時模型可能漏看幾筆. 合約比對因此由批次程式逐筆呼叫 LiteLLM, 每次只送一處差異與提示範本, 再把各筆回覆合併成差異說明表. 一定要在介面上操作時, 須對該檔案開啟「Using Entire Document」, 讓全文放進每則訊息 (來源: Open WebUI 文件 Retrieval Augmented Generation).

上下文與分段 ​

長篇合約不要一次整份送進模型. 合約比對只送差異清單; 法規對照一次只處理一條內部規定. Open WebUI 的檢索設定 (Top K, 切塊大小) 見 P1 的設定要點; 法規條文建議以一條為一段, 讓檢索結果與條號一一對應 (推論, 信心: 中).

驗收方式 ​

1. 合約比對測試組. 取一份已結案的合約, 由法務人員手動製作修改版, 刻意放入 20 處已知的實質差異, 涵蓋: 金額, 期限, 責任上限, 管轄法院, 「得」改為「應」, 刪除一個「不」字, 新增條款, 刪除條款; 另加 3 處只改標點或空白的排版差異. 通過標準:

  • 程式找出全部 20 處實質差異, 3 處排版差異在統一格式後不列入 (程式比對的結果固定, 解析正確時應為全數).
  • 模型的差異類型分類, 由法務人員逐筆評分, 記錄正確率.
  • 模型沒有新增清單以外的差異.
  • 差異說明表的筆數等於差異清單的筆數, 沒有漏列.

2. 法規對照測試組. 法遵人員先挑 20 條內部規定, 自行完成對照作為標準答案, 其中至少 3 條在法規中沒有對應. 通過標準: 對應條號全部存在於法規知識庫; 「無對應法條」的題目沒有編出條號; 對照結果與標準答案的一致率由法遵人員決定是否可接受.

3. 權限測試. 非法遵群組的帳號看不到法規對照的專用模型與知識庫 (測試方式見 E1); 合約比對的批次作業只開放法務群組執行, 其他帳號執行時遭拒 (推論).

4. 回歸測試. 上述兩組測試併入 M6.1 節的測試集, 換模型或升級後重跑.

風險與限制 ​

風險影響因應方式
不是法律意見讀者把模型的影響說明當成法律判斷輸出一律標示「不是法律意見, 須由專業人員確認」; 簽核流程保留法務人員的確認欄位
合約屬高度機密合約內容進入向量庫, 對話紀錄與 Langfuse只授權法務群組; 紀錄平台限稽核人員存取並設保存期限; 比對完成後刪除暫存檔
解析錯誤掃描 PDF 或表格解析錯誤, 導致差異清單有誤比對前預覽解析結果; 掃描檔以原始電子檔為優先
模型分類或說明錯誤低估一處責任條款的影響差異清單由程式產生, 解析正確時不會漏列; 每一處差異都由法務人員看過
引用過時或編造的法條依錯誤條文修訂內部辦法只用官方正式版本並記錄修正日期; 程式檢查條號存在; 法遵人員確認
法規解釋與實務見解條文之外的函釋, 判決與主管機關見解不在知識庫中本範例只做條文層級的對照, 解釋問題交給專業人員

需要人工確認的步驟: 每一處合約差異的影響判斷, 每一條法規對照結果, 以及所有對外回覆.
