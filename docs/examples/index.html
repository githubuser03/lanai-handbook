應用範例 ​

本頁屬性

  • 等級: ○ 依情境
  • 狀態: 可閱讀 (部分資料待核對)
  • 資料基準日: 2026-10-26
  • 待查證: 各範例的設定與指令依官方文件整理, 未實機驗證; 各頁的「待查證」列出個別事項; 本頁為索引, 來源見各範例頁與頁尾「資料來源」

結論: 範例說明組好的系統能解決哪些日常問題, 以及每個範例至少要組到哪些模組. 個人範例組到里程碑 1 或加上檢索即可; 企業範例多數需要里程碑 2, 會讓模型動手的範例才需要里程碑 3. 所有範例共用同一個原則: 模型負責整理與撰寫; 需要精確結果的工作 (計算數字, 找出文件差異) 交給程式; 會改變系統狀態或對外的動作由人確認.

範例對象需要的模組解決的問題
P1 問自己的文件個人M1, M2, M4把個人筆記, 手冊, 論文放進知識庫, 用自然語言提問並取得附出處的回答
P2 程式撰寫助理個人M1, M2 (需要執行程式時加 M7)在本機請模型解釋, 撰寫與檢查程式碼, 程式碼不離開本機
P3 會議記錄摘要個人M1, M2把逐字稿整理成摘要, 決議與待辦清單
E1 內部知識庫問答企業M0 至 M6讓同事依權限查詢內部規章, 手冊與歷史文件
E2 資安告警分流企業M0 至 M8由隔離模型整理告警內容, 代理依政策建議或執行處置, 高風險動作轉人工核准
E3 合約與法規文件比對企業M0 至 M6比對合約版本差異, 或把內部文件對照法規條文, 列出差異與出處
E4 每週報告自動化企業M0 至 M7, M9由 n8n 定期彙整工作紀錄與指標, 交給模型撰寫週報草稿, 經人工確認後寄出

每個範例依同一個格式撰寫: 情境, 需要的模組, 流程, 設定要點, 驗收方式, 風險與限制. 「需要的模組」一節標出每個模組屬於哪個里程碑; 「驗收方式」列出上線前可以照著做的測試題或檢核步驟.

閱讀建議 ​

  • 沒有工程背景的個人讀者: 從 P1 或 P3 開始. 兩者都只需要里程碑 1 的環境 (P1 另加 M4 的檢索), 不需要閘道, 帳號系統或代理.
  • 寫程式的個人讀者: P2 說明三種用法, 只有讓模型執行程式碼時才需要 M7 的沙箱.
  • 規劃企業導入的 IT 與資安人員: 先讀 E1, 它定義了部門, 群組與知識庫的權限模型, E3 沿用同一套設計. E2 與 E4 會讓系統動手做事, 分別示範代理加政策引擎, 以及固定流程加人工核准兩種做法.
  • E4 的模組備註: M9 的前置模組包含 M7. E4 只用到 M7 的工具閘道 (MCP gateway), 不需要程式碼沙箱.
範例會改變系統狀態或對外的動作人工確認的位置
P1, P3無讀者引用回答或寄出會議記錄前, 核對原文
P2用法 C 會修改檔案與執行指令合併程式碼前檢查差異
E1, E3無 (只查詢與整理)涉及權益或法律判斷時, 由承辦單位或專業人員確認
E2開工單, 隔離主機, 封鎖 IP 等A2 審查不一致與所有 A3 動作由分析師核准
E4寄送週報每份草稿寄出前由負責人核准, 對外發信屬 A3

由上表可見, 範例越往後, 系統能直接做的事越多, 人工確認的位置也越需要事先設計清楚; 動作分級 A0 至 A3 的定義見 E2.
