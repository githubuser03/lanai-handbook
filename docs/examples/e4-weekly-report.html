E4 每週報告自動化 ​

本章屬性

  • 等級: ○ 依情境
  • 狀態: 可閱讀 (部分資料待核對)
  • 資料基準日: 2026-10-26
  • 待查證: n8n 與 LiteLLM 設定依官方文件整理, 未實機驗證; n8n 的 OpenAI 憑證是否可改指向 OpenAI 相容 API, 官方憑證文件未說明, 因此本頁改用 HTTP Request 節點; 工具名稱 (ticket.list_closed 等) 為示意

結論: 每週報告是規則固定的流程, 適合交給 n8n 排程執行, 不需要代理自己決定步驟. n8n 經 MCP gateway 呼叫唯讀工具取得工作紀錄與指標, 由程式計算數字, 再經 LiteLLM 請模型撰寫文字說明; 草稿送給負責人確認, 確認後才寄出. 對外發信屬 A3 (不可回復), 一律人工核准, 而且核准由工具閘道再檢查一次, 不只靠 n8n 流程本身.

對象: 企業. 需要的模組: M0 至 M6, M9 (另需 M7 的工具閘道; 不需要程式碼沙箱).

情境 ​

一個 IT 維運團隊每週五要交週報給主管, 每月另交一份服務報告給外部客戶. 內容大致固定: 本週結案工單數, 尚未結案的重大事件, 系統可用率, 下週計畫. 承辦人每次要登入工單系統, 監控平台與工作紀錄表, 手動複製數字, 再寫成文字, 每次約需半天, 而且偶爾抄錯數字.

本範例把「收集數字」與「寫成文字」交給自動流程, 承辦人只負責檢查草稿與按下核准. 治理設計要回答三個問題: 數字對不對, 寄給誰, 以及誰同意寄出.

需要的模組 ​

模組里程碑在本範例的用途
M0 基礎環境里程碑 1自動化區, 閘道區, 工具區, 推論區, 稽核區 VM
M1 推論伺服器里程碑 1vLLM 執行撰寫草稿的對話模型
M2 使用者介面與反向代理里程碑 1n8n 的核准網址經反向代理提供; 反向代理只轉送 n8n 的 Webhook 路徑, 只限內網
M3 模型入庫與存放里程碑 2模型經入庫檢查
M4 檢索 (RAG)里程碑 2可選: 參考過去的週報格式
M5 模型閘道與身分驗證里程碑 2n8n 專用的 LiteLLM 虛擬金鑰, 限制可用模型與用量
M6 可觀測, 稽核與評估里程碑 2每次執行與每次工具呼叫的紀錄; 歷史週報當測試資料
M7 工具與沙箱 (只用 MCP gateway)里程碑 3工單, 監控, 郵件的 MCP 伺服器都經工具閘道呼叫
M9 流程自動化里程碑 3n8n 排程, 彙整, 等待核准

M9 的前置模組包含 M7: n8n 依本手冊的架構只經 LiteLLM 與 MCP gateway 對外, 本身不保存外部系統的金鑰.

流程 ​

[自動化區: n8n]
   |
   | 1. Schedule Trigger: 每週五 14:00 (工作流程時區設為 Asia/Taipei)
   v
[MCP Client 節點] --Streamable HTTP, Bearer--> [閘道區: MCP gateway]
   |   --> [工具區: 工單 MCP 伺服器] ticket.list_closed (A0)
   |   --> [工具區: 監控 MCP 伺服器] metrics.availability (A0)
   |   --> [工具區: 工作紀錄 MCP 伺服器] worklog.list (A0)
   v
[程式節點] 2. 計算數字, 填入週報的固定表格 (模型不經手數字)
   |
   v
[HTTP Request 節點] --POST /chat/completions, 虛擬金鑰--> [閘道區: LiteLLM] --> [推論區: vLLM]
   |   3. 模型只撰寫文字說明
   v
[程式節點] 4. 檢查草稿中的數字都來自第 2 步的計算結果
   |
   v
[MCP Client 節點] 5. 把草稿與核准網址 ($execution.resumeUrl) 送給負責人
   |   --> MCP gateway --> 內部通訊或工單工具 (A1, 內部可見)
   v
[Wait 節點] 6. On Webhook Call, 最長等待 3 天
   |
   +--> 逾時或拒絕: 不寄出, 通知負責人, 流程結束
   |
   | 負責人核准 (經反向代理呼叫核准網址, 需驗證)
   v
[MCP Client 節點] 7. mail.send (A3)
   |   --> MCP gateway 確認有對應的核准紀錄後才放行
   v
[收件者: 名單固定在郵件工具的設定中, 不由模型決定]

紀錄: [n8n 執行紀錄, MCP gateway 與 LiteLLM 呼叫紀錄] --> [稽核區] --> [既有 SIEM]

設定要點 ​

以下依 n8n 與 LiteLLM 官方文件整理, 未實機驗證.

排程與時區 ​

  • Schedule Trigger 節點可用 Weeks 設定 (每隔幾週, 星期幾, 幾點幾分), 也可用 cron 運算式, 例如 n8n 文件中的 0 12 * * 1 代表每週一中午.
  • n8n 文件說明, 排程依工作流程的時區設定; 沒有設定時用執行個體的時區, 而自架版預設為 America/New York. 因此要在工作流程設定中把時區改為 Asia/Taipei, 否則會在台灣時間的半夜執行.
  • 官方文件提醒, 使用 Schedule 觸發的工作流程要儲存並發布 (publish) 才會依排程執行.

取資料: MCP Client 節點 ​

  • n8n 的 MCP Client 節點設定伺服器傳輸方式與 MCP 端點網址, 支援 Bearer, Header, 多組 Header 與 OAuth2 驗證, 工具清單會自動從 MCP 伺服器取得 (n8n 文件). 端點網址指向 MCP gateway, 使用 n8n 專用的權杖.
  • n8n 這把權杖在 MCP gateway 只開放唯讀工具與 mail.send; 工單系統, 監控平台與郵件伺服器的帳密只存在工具區的 MCP 伺服器, n8n 看不到.

寫草稿: 經 LiteLLM ​

  • 用 HTTP Request 節點呼叫 LiteLLM 的 /chat/completions, 以 Authorization: Bearer <n8n 專用虛擬金鑰> 驗證 (LiteLLM 虛擬金鑰文件的呼叫方式). 金鑰以 /key/generate 建立時, 用 models 限定只能使用撰寫週報的模型, 並以 metadata 標明用途.
  • 這把金鑰存在 n8n 的憑證中. 它是內部閘道的虛擬金鑰, 不是外部系統的金鑰; 外洩時在 LiteLLM 停用即可, 不影響其他應用.

提示範本 (數字由程式填好, 模型只寫說明):

以下是本週維運資料, 表格中的數字已由系統計算, 不得修改, 不得自行計算新的數字.
請用繁體中文撰寫週報的文字段落:
1. 本週重點 (3 至 5 點, 每點一句).
2. 未結案重大事件的現況說明, 只根據事件清單中的描述.
3. 下週計畫, 只根據工作紀錄中標為「下週」的事項.
資料中沒有的內容寫「本週無資料」, 不要推測原因.

指標表:
{{metrics_table}}

事件清單:
{{incidents}}

工作紀錄:
{{worklog}}

範本中以兩層大括號標示的位置, 由 n8n 的運算式填入前一步的結果.

數字檢查 ​

草稿回來後, 以程式節點擷取草稿中的所有數字, 逐一確認出現在第 2 步的計算結果中; 有任何不在清單中的數字, 草稿標記為「需檢查」並在通知中註明 (推論, 信心: 中高). 這一步不能證明文字說明正確, 但能擋下模型自行算出或編出的數字.

人工核准與寄出 ​

  • n8n 的 Wait 節點支援四種恢復方式: 經過一段時間, 指定時間, 收到 Webhook 呼叫, 表單送出. 本範例用「On Webhook Call」. 每次執行都會產生唯一的恢復網址 $execution.resumeUrl, 可放進通知中; 恢復網址可以要求 Basic Auth, Header Auth 或 JWT 驗證 (n8n 文件). 設定驗證, 不使用 None.
  • 開啟「Limit Wait Time」, 例如最長 3 天. 官方文件說明, 逾時後流程會自動恢復, 因此逾時後的分支必須是「不寄出, 通知負責人」, 不能直接接寄信節點.
  • 寄信屬 A3. 核准狀態不只存在 n8n: 負責人核准時, 核准紀錄 (核准者, 時間, 草稿雜湊值) 同時寫入稽核區; MCP gateway 收到 mail.send 時, 先確認有對應的核准紀錄才放行 (政策判定方式同 E2 的 OPA 做法). 這樣即使 n8n 流程遭竄改, 也無法未經核准寄信 (推論, 信心: 中).
  • 收件者名單固定在郵件 MCP 伺服器的設定 (例如內部主管群組, 客戶的指定窗口), mail.send 不接受模型或 n8n 傳入的任意收件者.

驗收方式 ​

1. 歷史資料重跑. 以過去 4 週的資料執行流程 (不寄出), 和當時人工寫的週報比較:

  • 指標表的數字與人工版完全一致 (由程式計算, 應為 100%).
  • 文字說明沒有出現資料中沒有的事件或原因; 由承辦人逐週評分是否可直接使用, 或需修改幾處.

2. 核准路徑測試.

測試預期結果
負責人核准寄出一封信, 收件者與設定名單一致
負責人拒絕不寄出, 執行紀錄標為拒絕
等待逾時不寄出, 負責人收到逾時通知
不帶驗證資訊呼叫恢復網址n8n 拒絕, 流程維持等待
在 n8n 直接呼叫 mail.send (跳過核准)MCP gateway 拒絕, 留下紀錄

3. 網路邊界. 依 M9.4 節的要點, 從 n8n 的 VM 直接連工單系統, 監控平台與郵件伺服器都應失敗, 只能經閘道區.

4. 用量與時區. 虛擬金鑰超過設定用量時, LiteLLM 拒絕請求, n8n 收到錯誤並通知負責人; 排程實際在台灣時間週五 14:00 觸發.

風險與限制 ​

風險影響因應方式
數字錯誤主管或客戶依錯誤的指標做決定數字由程式計算並固定在表格; 程式檢查草稿中的數字
模型捏造事件或原因週報內容與事實不符提示範本限定只根據資料; 負責人核准前逐段閱讀
寄錯對象內部資訊外流給客戶或無關人員收件者名單固定在郵件工具設定; 對外發信一律人工核准
核准流於形式負責人沒看就按核准通知中列出「需檢查」的標記與本週與上週的差異; 定期抽查已寄出的週報
n8n 平台漏洞2026 年已有實際利用紀錄的漏洞 (見 M9.1 節)獨立 VM, 只能連閘道區; 鎖定版本並追蹤公告; n8n 不保存外部系統金鑰
恢復網址外洩他人可能代為核准恢復網址要求驗證; 核准網址只限內網經反向代理存取
報告含人員績效資訊工作紀錄可能涉及個人表現週報只呈現團隊層級的彙總; 執行紀錄設定保存期限
授權n8n 採 Sustainable Use License, 非 OSI 開源 (見 M9.1 節)依授權只做內部使用; 對外提供服務前先確認授權條款

需要人工確認的步驟: 每一份草稿寄出前的核准; 所有對外發信.
